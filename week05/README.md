# Docker 핵심 이론

## 1. VM 방식과 컨테이너 방식

### 하이퍼바이저 기반 VM

```text
┌────────────── VM ──────────────┐
│ 앱 A │ Guest OS │
├───────────────────────────────┤
│ 앱 B │ Guest OS │
├───────────────────────────────┤
│          하이퍼바이저          │
├───────────────────────────────┤
│          Host OS              │
├───────────────────────────────┤
│          Hardware             │
└───────────────────────────────┘
```

각 VM은 독립적인 **Guest OS**를 포함한다.

* VM마다 Guest OS가 필요하기 때문에 상대적으로 무겁다.
* OS 전체를 실행해야 하므로 시작 시간이 비교적 길다.
* OS 이미지가 포함되어 이미지 크기가 큰 편이다.
* OS 단위의 강한 격리가 가능하다.

### 컨테이너 기반

```text
┌───────────────────────────────┐
│ 앱 A │ 앱 B │ 앱 C │
├───────────────────────────────┤
│        Docker Engine          │
├───────────────────────────────┤
│       Host OS / Kernel        │
├───────────────────────────────┤
│           Hardware            │
└───────────────────────────────┘
```

컨테이너는 별도의 Guest OS를 실행하지 않고 **Host의 커널을 공유**한다.

* Guest OS가 필요하지 않아 상대적으로 가볍다.
* 필요한 프로세스만 실행하므로 시작이 빠르다.
* OS 전체가 아닌 애플리케이션 실행에 필요한 파일을 포함하므로 이미지가 상대적으로 작다.
* OS 전체를 분리하는 VM과 달리 **프로세스 수준으로 격리**된다.

> 핵심 차이: **VM은 OS 단위로 가상화하고, 컨테이너는 프로세스 단위로 격리한다.**

---

## 2. 컨테이너 격리

컨테이너는 Host와 커널을 공유하지만, 컨테이너 내부에서는 자신의 환경이 독립적인 것처럼 보이도록 만들어진다.

이를 위해 Linux의 **namespace**와 **cgroup** 등의 기능을 사용한다.

### namespace: "무엇을 볼 수 있는가"

namespace는 프로세스가 바라보는 시스템의 범위를 분리한다.

즉, **"안 보이게 만들기"**에 해당한다.

#### PID namespace

컨테이너 내부의 프로세스는 독립적인 프로세스 공간을 가진다.

```text
Host
├── PID 1
├── PID 200
├── PID 300
└── ...

Container
└── PID 1
```

컨테이너 내부에서는 자신의 메인 프로세스가 **PID 1**로 보이며, 일반적으로 Host의 다른 프로세스를 직접 볼 수 없다.

#### Network namespace

컨테이너는 독립적인 네트워크 공간을 가진다.

* 자신의 네트워크 인터페이스
* 자신의 IP
* 자신의 포트 공간

등을 가질 수 있다.

따라서 다른 컨테이너의 네트워크 환경을 그대로 볼 수 없도록 분리된다.

#### Mount namespace

컨테이너는 독립적인 파일 시스템 관점을 가진다.

```text
Host
/
├── home
├── etc
├── var
└── ...

Container
/
├── app
├── etc
├── usr
└── ...
```

컨테이너 내부에서 `ls /`를 실행해도 Host의 전체 파일 시스템이 그대로 보이는 것이 아니라, 컨테이너가 사용하는 파일 시스템을 기준으로 보인다.

> **주의:** 격리는 "서로 통신할 수 없다"는 의미가 아니다.
> 네트워크 설정이나 공유 디렉터리 등을 통해 컨테이너끼리 통신하거나 데이터를 공유할 수 있다.

## 3. cgroup: 자원 사용량 제한

**cgroup(Control Groups)**은 프로세스가 사용할 수 있는 시스템 자원을 제한하고 관리한다.

즉, **"얼마나 사용할 수 있는가를 제한"**하는 역할이다.

### Memory cgroup

컨테이너가 사용할 수 있는 메모리의 상한을 설정할 수 있다.

```text
Container
    │
    └── Memory Limit: 512MB
                 │
                 └── 제한을 초과하면 OOM 등의 처리 발생
```

### CPU cgroup

컨테이너가 사용할 수 있는 CPU 자원의 양을 제한하거나 관리할 수 있다.

따라서 여러 컨테이너가 하나의 Host에서 실행되더라도 특정 컨테이너가 시스템 자원을 과도하게 사용하는 것을 제한할 수 있다.

### namespace와 cgroup의 차이

| 기술        | 역할        | 관점              |
| --------- | --------- | ------------------ |
| namespace | 환경을 분리    | **무엇이 보이는가?**      |
| cgroup    | 자원을 제한·관리 | **얼마나 사용할 수 있는가?** |

## 4. 컨테이너와 커널 공유

Linux 컨테이너는 **Linux 커널을 사용한다.**

```text
Container A ──┐
Container B ──┼──→ Linux Kernel
Container C ──┘
```

컨테이너마다 별도의 커널을 실행하는 것이 아니라 하나의 커널을 여러 컨테이너가 공유한다.

따라서 컨테이너는 VM처럼 각각 독립적인 OS 전체를 실행하는 구조가 아니다.

### Docker Desktop의 경우

Windows나 macOS에서는 Linux 컨테이너가 Host OS의 커널을 직접 공유하는 것이 아니다.

Docker Desktop은 Linux 컨테이너를 실행하기 위해 **Linux VM** 등의 Linux 환경을 사용한다.

따라서 개념적으로는 다음과 같이 볼 수 있다.

```text
macOS / Windows
      │
      └── Linux VM
             │
             ├── Container A
             ├── Container B
             └── Container C
```

즉, **Linux 컨테이너가 필요로 하는 것은 Linux 커널**이라는 점이 핵심이다.

# 5. 이미지와 컨테이너

Docker에서는 **이미지(Image)**와 **컨테이너(Container)**를 구분해야 한다.

### 이미지

이미지는 컨테이너를 생성하기 위한 **읽기 전용 템플릿**이다.

애플리케이션과 실행에 필요한 파일 및 환경을 묶어놓은 형태라고 이해할 수 있다.

```text
Image
 ├── Application
 ├── Runtime
 ├── Libraries
 └── Configuration
```

### 컨테이너

컨테이너는 이미지를 기반으로 실제 실행된 **인스턴스**다.

```text
Image
  │
  ├── run → Container A
  ├── run → Container B
  └── run → Container C
```

하나의 이미지로 여러 개의 컨테이너를 생성할 수 있다.

### 클래스와 객체의 관계

개념적으로 다음과 비슷하게 생각할 수 있다.

```text
Class  ───────→ Object
Image ────────→ Container
```

다만 이미지와 컨테이너의 관계를 완전히 동일한 개념으로 보는 것은 아니며, **이미지는 컨테이너를 생성하기 위한 템플릿이고 컨테이너는 그 이미지로부터 생성된 실행 인스턴스**라고 이해하는 것이 정확하다.

---

## 6. 이미지와 컨테이너의 파일 시스템

이미지는 기본적으로 **읽기 전용** 레이어를 사용하고, 컨테이너가 실행되면 그 위에 컨테이너의 변경 사항을 기록하는 쓰기 가능한 레이어가 추가된다.

```text
┌─────────────────────┐
│ Container           │
│ Writable Layer      │
├─────────────────────┤
│ Image Layer         │
│ Read Only           │
└─────────────────────┘
```

따라서 컨테이너 내부에서 파일을 생성하거나 수정하면 컨테이너의 쓰기 레이어에 반영된다.

컨테이너를 삭제하면 해당 컨테이너의 쓰기 레이어도 함께 사라진다.

> 지속적으로 보존해야 하는 데이터는 일반적으로 **Volume** 등의 별도 저장 방식을 사용한다.

# 7. Registry

**Registry**는 Docker 이미지를 저장하고 공유하는 저장소이다.

```text
             docker push
Local Image ─────────────→ Registry
     ↑                         │
     │                         │
     └────── docker pull ──────┘
```

대표적인 Registry:

* Docker Hub
* GitHub Container Registry (GHCR)

### 주요 명령의 의미

```text
docker pull
```

Registry에서 이미지를 가져온다.

```text
docker push
```

내가 만든 이미지를 Registry에 업로드한다.

```text
docker run
```

이미지를 기반으로 컨테이너를 생성하고 실행한다.

전체적인 관계는 다음과 같다.

```text
                 Registry
                ↗        ↘
         docker push    docker pull
              ↑            ↓
          Local Image
               │
          docker run
               ↓
          Container
```

# 8. 전체 개념 정리

Docker의 핵심 구조를 하나로 연결하면 다음과 같다.

```text
                    Registry
                       │
                   Image 저장
                       │
                   docker pull
                       ↓
                    Image
                       │
                  docker run
                       ↓
                  Container
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
     namespace                    cgroup
   환경/시야 격리              자원 사용량 제한
          │                         │
          └────────────┬────────────┘
                       ↓
                 Linux Kernel
                       │
                    Hardware
```

### 핵심 키워드

* **VM**: Guest OS를 포함하여 OS 단위로 가상화
* **Container**: Host의 커널을 공유하며 프로세스 단위로 격리
* **namespace**: 프로세스가 볼 수 있는 환경을 분리
* **cgroup**: CPU, 메모리 등의 자원 사용량을 제한·관리
* **Image**: 컨테이너를 생성하기 위한 읽기 전용 템플릿
* **Container**: Image로부터 생성된 실행 인스턴스
* **Registry**: Docker Image를 저장하고 공유하는 저장소
